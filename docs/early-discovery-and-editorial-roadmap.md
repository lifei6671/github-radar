## 二、第一期实施顺序

### P0.1 人工发现与来源记录

- 在后台仓库管理增加「提交仓库」，接受多行 GitHub 仓库 URL 或 `owner/repo`，可附原始传播 URL 和备注。首期由管理员明确提供目标仓库，社交链接作为证据保存。
- 校验输入后将解析交给现有 Worker，返回逐条结果。通过 GitHub 仓库 API 确认公开身份，使用数字 ID 幂等写入，复用已有改名、屏蔽、租约和可见性规则。重复提交合并同一仓库，新的来源仍可记录。
- 保留现有 `search_observations`、`trending_observations` 和历史来源关系。为人工及后续社区信号增加事件记录，含仓库 ID、来源类型、来源标识或 URL、首次观测时间和可选备注。采集与发布沿用各自的资格校验，低 Star 候选可在后台复核。

验收覆盖重复 URL、仓库改名或转移、混合成功与失败、被屏蔽仓库、重启续跑和管理员手工重点监控。前台仍按既有发布条件开放仓库。

### P0.2 官方 Star 历史与双口径增长

GitHub 于 2026-09-04 发布 `GET /repos/{owner}/{repo}/stargazers/history`。接口按周由近到远分页，每页最多 30 周，`days` 从周日开始，统计边界未保证对齐 UTC。它适合建立历史 Star 创建计数，无法从该序列还原任意时刻的累计 Star 或真实净增。[GitHub 接口文档](https://docs.github.com/en/rest/activity/starring#get-repository-star-history) [GitHub 发布说明](https://github.blog/changelog/2026-09-04-new-api-endpoint-provides-privacy-safe-star-history-data/)

- 先用项目现有 API 版本和凭据对不同年龄的公开仓库做小样本探测，记录返回结构、周首时间戳、请求头、当前周完整性和限流行为。开发时先检查当前 `go-github` 是否已提供适用方法，接入沿用现有客户端的超时、预算和退避。
- 在独立历史表按 `repo_id + week_timestamp` 幂等保存七天计数、抓取时间和覆盖范围，允许上游更新同一周。首轮只取最近一页，并截取业务需要的近期窗口。历史分页回补放到按需任务，设总页数和请求预算。当前日、未返回日和确认为零的日期分别表达。
- 初次收录优先探测近期日计数，已有本地快照后并列展示两条证据。历史任务失败时保留已有数据和失败原因，本地采样继续。图表与筛选明确区分「GitHub 历史日 Star」和「本地窗口净增」，历史点不进入本地累计快照表。
- 新增独立爆发信号。精确 24h 净增 ≥100，且相对前 7 个独立日窗的平滑倍数 ≥2.5 时命中。初始公式为 `(当前净增 + 10) / (此前日均增长 + 10)`。此前至少 5 天有合格观测，对这些日期的净增取非负值后求日均，缺测日不计入。精确 24h 净增 ≥500 可直接命中。仅有官方日计数时，用同源已完成日比较并标记为待确认爆发，待本地快照复核后晋级。阈值、覆盖天数和同源口径均记录在入档依据里。

验收覆盖零增长基线、缺日、当前日未完成、分页顺序、重复回补、限流、无法访问以及仓库改名。任何 GitHub 历史数据都不能把本地 24h 净增窗口从缺测变为精确。

实施记录（2026-11-13）：用本地应用的凭据和 `2026-03-10` API 版本验证 `tonhowtf/omniget`、`meta/astryx` 和 `octocat/Hello-World`，均返回 `200`。响应使用 Core 额度（样本窗口上限 5,000），`Link` 使用数字仓库 ID；旧仓库的第 2 页紧接第 1 页。样本周首为周日 `00:00 UTC`，GitHub 不保证所有响应均为 UTC。当前周已返回七个元素，未来零值不能视为观测。另对不存在的公开名称验证了 `404`；退避由固定响应测试覆盖，未耗尽真实令牌额度。

自动探测只取最近 5 周，成功或终态失败后最早隔日再探测。管理员可从后台仓库详情回补最多 3 页、每页 30 周；页与页之间复核周边界。历史请求与身份复核合计使用独立的每小时 120 次本地预算，同时受 Core 预算约束。详情用独立柱图显示官方日计数，用原有折线显示本地累计和窗口净增。「全部项目」可按本地已确认或 GitHub 待确认爆发筛选。S 档由本地爆发触发时保留实际阈值、覆盖日数、来源和判定值。

### P0.3 滚动早期发现与规则运行记录

| 仓库年龄 | 起始 Star | 扫描间隔 |
| --- | ---: | ---: |
| 0–3 天 | 10 | 2 小时 |
| 4–14 天 | 50 | 4 小时 |
| 15–30 天 | 150 | 12 小时 |

- 以每轮计划的 UTC 日期为锚点，按创建日期差计算三个互斥主窗口。任务入队时固化边界，跨日重试复用原计划。补扫与主窗口独立标识，先试回看 24 小时，并使用数字 ID 合并重复命中。
- 先上线全局三窗和少量关注领域的独立查询，Topics 与关键词分开配置。账号查询复用现有 Search，避免为每个专题自动复制扫描规则。
- 复用现有分页、Star/日期分片及不完整结果检查。新增按规则和计划槽归并的运行记录，包含上游总量、分片完成数、唯一仓库数、新增数、延迟、失败原因和是否完整。初期只对连续异常、配额积压或长期未跑发后台提示，阈值在试运行后调整。

验收覆盖三个窗口的边界日期、同一仓库跨来源重复命中、索引延迟补扫、超千条分片和不完整结果。GitHub Search 支持累计 Star 排序，最近 24 小时净增由本地证据计算。搜索配额单独计量，已认证的常规搜索上限为每分钟 30 次，运行时以实际限流响应为准。[GitHub Search 文档](https://docs.github.com/en/rest/search/search#search-repositories) [GitHub REST 配额说明](https://docs.github.com/en/rest/using-the-rest-api/rate-limits-for-the-rest-api)

首次启动新版本时安装三条全局滚动规则，以及独立的 MCP Topics 和 coding agent 关键词规则。每条滚动规则每天补扫一次，补扫窗口以主扫描的 UTC 日期往前平移 24 小时。规则配置、扫描记录和异常提示都在后台「发现规则」。开工延迟从计划槽起算。Search 的上游总量来自首页，完成分片在最后一页结算，仓库数按数字 ID 统计。运行记录沿用发现数据的保留期。

### P0.4 观察池晋级、冷却与容量

| 现有档位 | 试运行用途 | 初始上限 | 采样周期 |
| --- | --- | ---: | ---: |
| S | 爆发 | 30 | 1 小时 |
| A | 重点 | 150 | 4 小时 |
| B | 普通 | 400 | 24 小时 |
| C | 冷却 | 1,000 | 72 小时 |

- 将表中参数作为试运行配置，先评估当前已监控仓库数和配额再应用。满额时保留人工关注的有效优先级，再按证据强度、增长和相关性分配容量。未获监控容量的候选保持可复核。
- 新仓库累计 Star ≥20 且精确 24h 净增 ≥15，可进入普通观察；精确 24h 净增 ≥50，可进重点观察。爆发信号优先判定，人工重点可跳过 Star 和增长门槛，仍受总容量及公开身份约束。
- 每次变更记录时间、旧档位、新档位和触发依据。连续 48 小时放缓可降为普通。具备可比样本时，连续 7 天低于同类基线可进入冷却。连续 14 天具备有效观测且缺少增长和新传播信号时可暂停，保留已收录资料。缺测中断连续判定，暂停仓库可因新的爆发证据或人工操作恢复。
- 满载快照平均约 2,353 次/日。Search、历史回补、README 和其他 GitHub 请求单独估算并统一计入各自资源预算。复用 Core/Search 的分桶、本地软限额、服务端重置时间、次级限流和人工任务优先机制。

验收包括无快照初收录、历史证据转实测、绝对增长优先、满额降档、缺测、人工重点、进程重启以及限流恢复。先用当前数据库离线演算旧规则与试验规则的差异，再开启自动晋级。

实施记录（2026-11-13）：后台「运行配置 → 调度」可以只读演算，填入试运行参数后保存即生效。档位变更和暂停原因见后台仓库详情的「监控记录」。升级保留已保存的运行设置。本地库副本演算从 5,000 个活跃仓库调整到 1,580 个，其中 3,420 个退出定时采样，已有仓库资料和快照继续保留。

首轮以新收录、Star 达标或传播、官方爆发信号安排有限探测。首采建立基线，约 24 小时后复采，自动探测每小时最多创建 20 个任务，并计入仓库采样预算。官方历史只触发复核。连续 7 天冷却以同语言、同 Star 量级且同日的项目中位值为基线，每天至少需要五个其他项目提供精确样本。14 天暂停按当前档位的实际采样间隔检查连续覆盖，期间出现 Star 增长、新 Trending 观测或新传播链接会保留观察。

### P0.5 公众号选题评分与人工复核

- 在已有选题记录上增加分项及证据。普通读者需求 30、演示效果 20、项目热度 20、实测与复现 20、话题新鲜度 10。全局热度继续独立展示。分项记录来源、评估版本和置信状态，缺乏实测时明确标为待验证。
- 先给出三个建议区间。≥80 优先准备，≥65 且 <80 进入候选，低于 65 继续观察。人工决定保留为独立状态，可写覆盖理由。升级时原有已发布、反馈和评分保留，旧评分明确标记版本。
- 模型复用已有摘要与队列预算，负责提炼读者收益、可演示场景、写作角度和实测步骤。排名、入池与档位由规则和可追溯信号计算。选题卡可查看仓库、README、增长和传播证据，涉及执行代码、系统权限或个人数据的项目记录人工核验结果后再用于公众号推荐。

验收用一组高热度但难演示、低热度但高读者价值、缺少证据、重复发布和重大版本更新的样本，核对排序和人工状态保留。第一期到此即可开展 14 天试运行。

实施记录（2026-11-13）：后台选题池展示五项分数、来源、置信状态和建议区间。已有分数标记为旧版，候选可重新评分，原评分写入历史。复核可以记录实测结果和覆盖理由，已识别的风险需要人工通过才能采用或发布。发布版本重入支持使用人工发现的 GitHub Release 链接作为证据，已发布状态和反馈保留在往期复核。新生成的导读可在同一模型响应中返回选题材料，现有导读缓存继续复用。

## 四、试运行与交付验收

连续运行 14 天。试运行前固定阈值版本、统计时区和外部对照榜，按天记录搜索覆盖、历史请求成功率、各档容量、晋级理由、人工复核结果和耗时。

| 指标 | 计算口径 | 首轮目标 |
| --- | --- | ---: |
| 提前发现率 | 对照榜首次出现的唯一仓库中，系统在该观测之前已收录的比例。排除对照覆盖不完整的日期并报告样本量。 | ≥40% |
| 有效候选率 | 每日榜前 20 个中，人工标记值得进一步检查的比例。当天不足 20 个时报告实际数量。 | ≥50% |
