# GitHub Radar 仓库采集准入与 AI 预算调度技术方案

> 目标：尽量不漏掉有潜力的 GitHub 项目，同时限制低价值仓库对采集队列、README 清洗和模型调用额度的消耗。
>
> 适用：本地 github-radar，Go + Gin + GORM + SQLite；执行前重新确认工作区状态与最大 goose 迁移号。
>
> 状态：后端改造已实现，迁移和回测见文末。连续 14 天在线观察尚未执行。本文件不包含发现页 UI 实施。
>
> 运行额度更新：当前默认每天 5,000 次（UTC），自动 4,500 次，人工 500 次。下文的 1,000 次及其分配数字记录初版设计。当前自动通道按 50%、30%、10%、10% 分配，UTC 中午后共享自动余量。

## 1. 核心约束

1. **召回率优先**：继续允许低 Star 仓库被轻量发现，不把 200/500/1000 Star 当作 Search 的全局最低门槛。
2. **分开四种资源行为**：轻量发现（保存元数据）、短期探测（有限首采与复采）、持续监控（S/A/B/C 分档采样）、AI 清洗（模型摘要、翻译、主题、向量等）分别准入。
3. **累计 Star 门槛只控制常规监控资格**；有可信增长、官方爆发、GitHub Trending、人工重点等信号时允许例外。
4. **AI 准入独立于发现页发布资格**。现有发现页发布条件需要 ready 中文摘要，AI 首次准入不得要求先通过发布条件或已有发现页记录，否则循环依赖。
5. **统一 AI 全局额度**：UTC 自然日最多 1000 次模型请求，自动至多 900、手动保留 100；所有模型链路包括 Embedding 都必须进入同一计量系统。1000 是上限，不是每日用满的目标。
6. **保留历史资产**：不重新编号仓库、不删除已发布归档、不修改原始综合热度算法、不改变 Star 历史口径；发现页当天动态入选和历史冻结由 `docs/discovery-daily-ranking-design.md` 单独处理。
7. **遵循 AGENTS.md**：核心代码中文注释，数据库优先 GORM 简洁查询，尽量不用 SQLite 方言；任何 UI 更改必须另行获得用户明确授权。本期先做后端、测试与文档。

## 3. 四层采集流水线

| 层级 | 状态与目的 | 允许消耗 | 退出/晋级 |
| --- | --- | --- | --- |
| L0 轻量发现 | Search、Trending、人工 URL，保存仓库数字 ID、元信息、来源 | 搜索 API / 少量 SQLite 写入 | 条件不够则保留候选，不自动进行全文 AI |
| L1 潜力探测 | 对部分候选采首个 Star 快照，约 24h 后有限复查，或使用已有官方 Star 历史信号 | 明确上限的 GitHub 仓库 API | 按真实增长或可信来源晋级，否则冷却 |
| L2 持续监控 | 按分龄常规规则或例外信号取得监控资格，进入 S/A/B/C | 周期性采样，受 GitHub 配额和档位容量约束 | 连续低增长时按证据降档/暂停 |
| L3 AI 清洗 | 通过独立质量预检、增长/探索优先级 | 摘要、翻译、主题分类、向量等模型调用 | 同指纹复用结果，失去资格时停止自动任务 |

四层是业务能力，不建议为每层新增一个互斥 `repositories.state`。复用已有 candidate、active、paused 状态和观察档位，新增独立的准入决定与原因数据。

### 3.1 常规持续监控门槛

建议使用 UTC 日期差计算仓库完整年龄天数：`age_days = max(0, utc_date(now) - utc_date(github_created_at))`；字段为 GitHub 返回的真实创建时间。项目实现需要统一这种日期口径并测试时区边界。

| 年龄 | 累计 Star 至少 | 附加要求 | 理由码 |
| --- | ---: | --- | --- |
| 0～7 天 | 200 | — | `age_7d_stars_200` |
| 8～14 天 | 500 | — | `age_14d_stars_500` |
| 15～30 天 | 1000 | — | `age_30d_stars_1000` |
| 30 天以上 | 1000 | 最近 15 天 `github_pushed_at` 非空且够新 | `established_active` |

以上四组互斥、任一满足即可取得「可分配常规监控席位」资格，不代表一定激活（仍受总容量和优先级约束）。

- `github_pushed_at` 是最近一次推送的代理指标，不等同于默认分支的实质功能更新。
- GitHub 创建时间缺失、未来异常时不得按新仓库处理；暂缓常规门槛，交由可信增长/人工信号决定。
- 是否 fork / template / mirror 属于质量信号而非绝对拒绝；对于重要派生工具可豁免。
- 不能将门槛同步覆盖到 Search 规则或现有发现页排序公式。

### 3.2 高召回率例外通道

以下证据允许不满足累计 Star 门槛的仓库进入短期观察：

1. 有精确 24h 增长 ≥15：普通观察；≥50：重点观察；≥100 或明确爆发：高优先级。
2. 当前 GitHub Trending 全站日榜前列、官方 Star 历史给出近期可验证的爆发信号：给予复采与监控竞争资格。历史每日点赞计数不可当成本地精确 24h 净增。
3. 管理员标记重点：跳过自动热度和内容门槛，但仍遵守 GitHub 可见性、系统总采集容量。
4. 小仓库的弱增长/传播信号：低频探索抽样，补齐证据后再决定，不强行开高频或直接调用模型。

增长证据必须记录类型、起止时间、精确度及来源，避免单纯使用累计 Star 伪造增长速率。

### 3.3 监控资格滞回与降档

- 创建第 7 天、230 Star 已进入监控的仓库，不因第 8 天突然需要 500 Star 而立即暂停。
- 年龄跨档后设置 72h 的保护观察窗口；随后结合精确增长、连续低增长、同类基线、容量和原有 48h/7d/14d 降档规则逐级退出。
- 一次性丢失窗口或 GitHub 限流不是负增长证据，不得作为快速退出理由。
- 已人工关注、已有高质量中文摘要或选题正在写作的仓库优先保留必要可用性；仍允许正常降低自动采样频率。
- 保留完整升降档与拒绝理由，后续可信爆发可从 paused/candidate 恢复。

## 4. L0/L1 的廉价预检与探测容量

### 4.1 不调用 AI 的 Preflight

使用现有元数据和有限 README/描述检查，返回 `pass / defer / reject`、理由码和 `next_check_at`：

- 拒绝：私有、禁用、屏蔽、身份冲突、明确不可访问（遵守已有恢复复核路径）。
- 暂缓：缺可读的描述或 README、没有可信增长/传播线索、无法判定主题、来源暂时不可用。
- 通过：仓库有有效功能描述/用法，或有可信增长、人工、Trending 信号。fork、自动生成项目和模板应降低优先级而非简单一律拒绝。
- 已存在相同 README 指纹且生成过有效完整摘要：复用，不再执行完整模型；仅内容实质变化或人工强制允许再处理。
- 不能机械采用 README 最低字数过滤：几十行 README 的工具也可能完全可用。

**Preflight 不依赖 ready 中文摘要、不依赖 PublishableRepositoryCondition**，因此首次清洗不会与发布资格形成循环。

### 4.2 探测预算与排序

沿用 `scheduleObservationProbes` 的限额与 24h 复查机制，优先级由高到低：

1. 已安排的真实 24h 复采，优先保护精确窗口；
2. 官方爆发、Trending、人工传播证据；
3. 接近分龄门槛、增长迹象明显的新仓库；
4. 新仓库低 Star 分层探索的随机样本。

单个无新证据的候选，首轮最多 1 次首采 + 1 次窗口内复采；不能因为多次 Search 命中反复占探测队列。以后出现新的可信信号时才允许开启新观察周期。

若没有配置 `ObservationPool`，当前 `admit()` 仍有直接激活分支，需要在旧模式下增加相同准入约束，或经过迁移测试后开启观察池模式；不能留一条旧路径绕过门槛。

## 5. 独立的 AI 准入与任务治理

### 5.1 AIEligible 的输入与输出

建议新增共享规则函数：`AIEligible(repo, signals, task_kind, now) -> allowed, lane, priority, reason, retry_at`。

准入基于：公开安全状态、分龄与增长、可信来源、README/描述质量、是否有相同指纹缓存、是否人工请求、模型任务类型、当日额度与调用队列负载。

| 通道 | 触发条件 | 处理 |
| --- | --- | --- |
| manual 人工 | 管理员请求或明确关注 | 独立保留额度，优先；不得绕过安全和物理模型限额 |
| growth 高增长 | 精确 24h ≥100、明确爆发或强 Trending 信号 | 首次完整中文摘要优先 |
| exploration 探索 | ≤30 天且有一定 Star/传播线索，通过廉价质量预检，但缺完整增长证据 | 按年龄和 Star 分层抽样，保留新项目召回 |
| revival 复热 | 老仓库近期新增增长/传播证据 | 对新变化复核，优先复用既有摘要 |
| maintenance 维护 | 高价值旧仓库的真正内容更新，必要的主题/翻译/向量 | 低于首次清洗优先级 |
| defer | 只有累计 Star、无证据、无实质内容或模型结果未变 | 不生成自动模型任务 |

**探索分层抽样**：建议同年龄段、Star 档中，70% 的探索配额按初步潜力排序，30% 使用按「UTC 日 + 数字仓库 ID」确定的稳定随机抽样。避免所有探索机会都由当前热门项目占满。比例为可调初始试验值。

### 5.2 自动清洗的三个门闩

统一检查必须同时覆盖：
1. `summary.Schedule()`：自动摘要、翻译、只有主题补全、缓存回填等全部自动来源的入队入口。
2. `summary.Queue.claimReady()`：旧积压任务领取前重验资格，失效任务取消或延迟并保留原因；人工任务豁免自动质量门槛。
3. `summary.Engine.runJob()` 和所有 Provider 发送前：最新公开状态、调用幂等和统一额度检查；不能由“已有旧摘要”“缺 Topics”旁路。

相同版本的 README 和相同模型/提示词指纹禁止重复完整清洗；等待确认的 `sending/unknown` 调用不能强行重试。已用完配额时不排出大量无效 pending 任务，也不通过低优先级主题分类把额度消耗光。

已经入选发现页并归档的项目，后续停止自动 AI 不影响历史名次；当天发现页的后续资格仍按独立方案执行。

## 6. 1000 次 AI 全局请求预算

### 6.1 额度定义

统一按 **UTC 自然日** 计量，与现有 `summary/budget.go` 一致；发现页的北京时间日界是另一个独立概念。

| 模型任务池 | 每日软配额 | 优先目的 |
| --- | ---: | --- |
| growth 首次清洗 | 450 | 已验证高增长项目 |
| exploration 早期探索 | 270 | 留出早期项目机会 |
| revival 老仓库二次爆发 | 90 | 复热项目 |
| maintenance 维护/翻译/主题/向量 | 90 | 已有优质项目维护 |
| manual 人工独立上限 | 100 | 人工指令优先 |
| **合计** | **1000** | **全局硬上限** |

- 自动 4 类之和最多 900，按通道软分配；某通道空闲且过半天，可将未用配额借给其他自动通道，但总自动上限不可超过 900。
- 人工 100 独立保留，不向自动请求借出；手动用完后明确告知当日额度耗尽。
- 若当天只有 200 个值得处理的仓库，就只运行相应任务；不强制填满 1000。
- 除次数外统计每次输入/输出 Token、模型、费用及耗时；可配置金额软/硬上限，避免大 README 或高价模型使成本失控。
- 总请求次数包括摘要生成、README 模型翻译、模型主题归类、AI 报告、相似项目 Embedding 以及未来新 Provider；**GitHub REST、普通 README 获取不计入模型调用**。

### 6.2 当前预算系统需要补足的部分

现有 `ai_calls` 在 `summary/budget.go` 按 `origin=auto/manual` 和 UTC 日预留调用，但 `embedding/provider.go` 直接请求独立模型端点，不在同一个调用账本。只把 `autoDailyCalls` 调为 900、`manualDailyCalls` 调为 100 无法保证所有模型请求之和不超过 1000。

推荐构建统一 `AIBudget` 服务，所有 Provider 在实际网络请求发送前都必须向该服务申请额度；原 `ai_calls` 保留调用详情。

可新增 `ai_budget_reservations` 轻量表记录：

`reservation_key、origin、lane、operation、provider、model、reserved_at、sending_at、settled_at、status、source_call_key`。

要求：
- 预留、检查自动池/人工池/总额以及写入操作在同一个数据库事务中完成。复用现有 SQLite 单实例写锁/短事务策略，避免并发超额。
- 有唯一逻辑请求键；一次新的**实际外部发送尝试**必须对应唯一预算占用，不允许复用旧键免费重发。
- 在实际发送之前更新成 sending；成功/失败/超时/未知都按已尝试请求计入预算，避免重试和重启造成漏计。
- 对于可证明确实未发送的过期预留，可以按现有安全状态机处理；已经 sending/unknown 的不得作为免费空槽释放。
- 新台账启用当天，要将当天已有 `ai_calls` 预留/调用按唯一键迁入或映射，防止切换时丢计和双计。
- 全局配额从持久数据库读取，重启或切换配置不应清零。
- Embedding 必须接入统一预算。考虑其当前无独立 Job 的实现，可以通过通用预留键按 repo ID + 输入指纹 + 实际发送序号生成；相同向量指纹使用原有缓存。
- 所有模型网络调用都要统一使用该服务；旧 Provider 不能保留另一条绕开额度的入口。

### 6.3 吞吐量与并发

现有默认摘要 Worker 为 1、调度候选查询 LIMIT 100；预算提高到 1000 只是理论上限，需要压测实际完成速度、GitHub README 请求预算、模型提供方的速率/并发上限和 SQLite 写锁延迟。

建议先保证预算一致性与任务幂等，再试运行 2～3 个 Worker 和合理批次；不把并发设置成 1000。次级预算如 GitHub API 配额和每小时 README 额度保持独立，不能用模型调用上限推算 GitHub 采样容量。

## 7. 持久化、清理及与现有系统兼容

尽量复用已有：
- `repositories`：数字 ID、状态、Stars、创建/推送时间、人工关注；
- `latest_metrics` / 官方 Star 历史及快照：可信增长证据；
- `repo_discovery_events`：传播来源；
- `ai_summaries`、`summary_checks`、`repo_readme_documents`：结果与指纹缓存；
- `jobs`、`ai_calls`：任务与调用证据。

新增最小 `repo_admission_decisions` 或等效结构，建议含：

`repo_id、admission_state(discovered/probing/monitoring/deferred)、reason、evidence_at、next_check_at、preflight_state(pass/defer/reject)、preflight_reason、policy_version、updated_at`。

该状态不能简单覆盖 `repositories.state` 的现有枚举。通过统一策略函数返回原因码，并将自动降档、人工豁免、缓存命中、AI 暂缓原因存档，便于漏判复盘。

清理规则：
- 普通低价值候选保留轻量元数据约 30 天，7 天无信号可降到低优先级；
- 清理积压任务只处理 pending/failed 等未发送自动任务，sending/unknown 按原调用结算状态处理；
- 已经发布、人工关注、选题涉及、历史发现归档涉及的仓库保留必要身份与记录，不被候选清理级联误删；
- 新增的 AI 调用配额台账保留足以追踪账期与审计的数据，按独立清理周期处理，不与原始 Star 快照清理混用；
- 存量低价值仓库分批降档或暂停，不做一次性全量停采，也不删除成功生成的中文摘要。

## 11. 实现与运行说明

| 阶段 | 本次实现 |
| --- | --- |
| P0 | `internal/domain/admission` 提供纯规则，后台在排队、领取、发送前分别复核；旧队列每轮最多检查 40 条待发任务。已发、发送不确定及人工任务保留原状态机。摘要、主题、译文和向量按版本复用。管理员关注绕过质量门槛，其后台工作仍走自动池。 |
| P1 | 分龄规则使用 UTC 日期差；两种分档均采用准入门槛，已跨档项目有 72 小时保护。探测每小时最多安排 20 条、未决最多 40 条，真实复采排在首采前。现有观察池容量保持配置决定，低频冷却、正常降档和人工关注仍生效。 |
| P2 | `internal/aibudget` 在发送事务中检查并记账。摘要、主题、翻译、报告、仓库向量和搜索向量共享同一账本；公开语义搜索走自动维护通道。UTC 中午前按 450/270/90/90 保留自动通道额度，中午后自动通道共享余量。发送失败、超时和未确认都计入次数。 |
| P3 | 管理员接口 `GET /api/v1/system/admission?day=YYYY-MM-DD`、离线 `admission-audit` 命令和队列日志提供日级计数、原因、耗时、Token、费用及抽查样本。准入日记录保留 45 天，已结算账本保留 90 天；未决请求不按普通历史清理。 |

迁移由现有 Goose 入口执行：

1. `00031_repo_admission.sql`：仓库派生标识、各入口最近准入决定。
2. `00032_ai_budget.sql`：独立发送账本，按旧调用键迁入历史详情。明确未发送的预留不占用额度；旧记录缺少准确发送时间时使用原始时间与耗时推算。恢复旧备份时，停机门禁内将目标库当日和前一日已发送记录及更早未决记录按键合并到待恢复副本。
3. `00033_admission_audit.sql`：日级准入记录、真实探测计数、监控席位读数及首次就绪导读。迁移前未记录的准入原因或日级计数无法回填。

升级旧库时，先备份，然后用同一个新版本完成迁移和启动，避免旧 Worker 在新账本启用后继续发送。需要回退策略时，在已有运行设置中开启 `ai.summary.legacyAdmission` 或 `scheduler.legacyMonitoring`，保留迁移和账本；旧二进制不会执行全局预算。新配置默认自动 900、人工 100、摘要 Worker 1，旧库显式设定的较小额度保留，超过上限的旧值按上限读取。金额使用配置的模型单价；未返回用量的条目与已知费用分开，配置硬金额时应为所有启用的模型填入同一币种单价。

14 天验收从策略开始记录的首个完整 UTC 日起算。每日固定保存全站榜单前十或人工确认的数字仓库 ID，使用以下命令产出对照：

```powershell
go run ./cmd/radar admission-audit -db <已迁移数据库副本> -from YYYY-MM-DD -days 14
go run ./cmd/radar admission-audit -db <已迁移数据库副本> -from YYYY-MM-DD -sample 123,456 -simulate -queue
```

`-sample` 适用于当日独立人工榜单；每个日期使用对应的样本 ID。普通查询和 `-simulate` 只读，后者只模拟当前副本的仓库集合；`-queue` 在副本上回滚真实排队事务，不领取任务、不请求 GitHub 或模型。每天分别记录：本地库没有身份、没有保留 Search 观测、已有候选但准入过滤、尚未评估、已准入。Search 观测按原配置清理，缺记录不能证明从未命中。按 0–7、8–14、15–30、31+ 天和 Star 档检查随机样本的实际用途、传播与后续增长，将“抽查确认有价值但被过滤 ÷ 已复核的过滤样本”分层报告。数据没有覆盖的日期标记缺样，不计算漏判率；入队或撤销数量也不能直接等同于已节省的外部请求。

模型次数和 GitHub 配额独立。探测理论排队上限为 480 条/日；单一观察周期正常只做 2 次采样。以 1,580 个满配观察席位和 60/240/1,440/4,320 分钟周期计算，30/150/400/1,000 的 S/A/B/C 理论合计约 2,353 次计划采样/日，另有探测、身份复核和 README 等请求，仍受原 GitHub 限额和实际调度约束。模型每日上限不是吞吐承诺；900 次自动请求平均每 96 秒一次。真实供应商速率、错误率和 GitHub README 预算未测量前，保持现有 Worker 设置。
